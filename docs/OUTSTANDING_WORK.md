## 2. Confirmed real, not yet fixed

- **`workers_comp`'s `checkCoidaOverdue`** (a weekly scheduled Cloud Function, `firebase/functions/src/index.ts`) queries `incidents.coidaSubmitted` for its overdue-COIDA-claim alert — but grep confirms **nothing anywhere writes that field**. The real signal for "was a COIDA claim actually filed" lives in `workers_comp`'s own `coida_claims`/`WorkersCompClaim`, written by `claims_tab.dart` — but `WorkersCompClaim` has no `incidentId` field linking it back to the originating incident, so there's no clean correlation today. Fixing this properly needs: adding an `incidentId` field to `WorkersCompClaim` (schema change), updating `claims_tab.dart`'s create flow to capture it, and repointing the scheduled function's query. Small in scope but touches a schema + a live write flow, so flagged rather than rushed.
- **`people`'s `Employee` vs `EmployeeProfile` duplicate models**: confirmed both genuinely live (not orphaned) — `Employee` (`employee.dart`) is used by the cross-module `employeesProvider`, consumed outside People too (e.g. `customer_service/widgets/ticket_form.dart`); `EmployeeProfile` (`hr_models.dart`) is used by People/HR's own routed screens. No single owner. A real but moderate-sized unification project (touching multiple modules) — worth scoping properly before starting, not a quick fix.
- **`people`'s `HrHubScreen` (`/hr`) vs `PeopleHubScreen` (`/people`) duplicate hub screens** — found 2026-08-12 while auditing launchpad reachability for the D365 IA reorg. Both are real, live, manager-facing HR dashboards with overlapping headcount/compliance metrics; only `PeopleHubScreen` is on the main launchpad — `HrHubScreen` is reachable only via a Control Tower quick-link KPI tile and 2 notification deep-link types (`leave`/`training`). Same "two competing implementations, no single owner" shape as the `Employee`/`EmployeeProfile` item above — worth deciding whether to merge, or make one the canonical HR landing screen and repoint the other's callers, rather than leaving both live indefinitely.
- **`people`'s `OkrDashboardScreen`** (`okr_dashboard_screen.dart`, 768 lines) — found 2026-08-12 during the same audit. Zero callers anywhere, and its own top-of-file comment reads "─── Mock Data Models ───": every `_Objective`/`_KeyResult` on screen is hardcoded, not a Firestore read — a direct `AGENTS.md` §3 violation if it were ever linked in as-is. Not part of the D365 masterplan's HR feature list either (no OKR mention). Needs a decision: build it for real (a new `Objective`/`KeyResult` model + collection + write paths) or delete it as abandoned scaffolding — deliberately left unlinked rather than wired into the launchpad reorg with fake numbers.
