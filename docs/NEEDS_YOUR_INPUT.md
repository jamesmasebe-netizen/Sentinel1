## Product & naming decisions

These came out of re-reading all 28 per-module audit docs' own "Open Questions" sections (`docs/modules/*.md` §8) — a lot of them have been silently resolved by two weeks of engineering work since, but these genuinely haven't, and none of them are things an agent should just decide on your behalf. **All 8 below were decided by the user 2026-08-12 and implemented the same day** — kept checked off, with resolution notes, per this file's own maintenance contract (a record of what was decided, not just that it was).

- [x] **`dashboard`/`executive` split.** *Decision: merge them.* Turned out already functionally merged — no separate `executive/` module exists, `DashboardScreen` already embeds `ControlTowerScreen` behind a toggle, and there was only one launchpad tile pointing at it. Renamed that tile from "Global Control Tower" to "Dashboard" to match. *Raised 2026-07-28, resolved 2026-08-12.*
- [x] **Training's `courses`/`enrollments`/`training_enrollments`/`training_records` split.** *Decision: use the best-practice consolidation method.* `enrollments` and `training_enrollments` turned out to be the identical concept (self-paced vs. manager-assigned course progress) split for no real reason — unified onto one collection (`enrollments`) with a `source` discriminator. `training_records` (completion certificates) is a genuinely different concept and stayed separate, but gained a real typed model (`TrainingCertificate`) where it only had raw maps before. `courses` (the catalog) was untouched. *Raised 2026-07-28, resolved 2026-08-12.*
- [x] **`health`'s `medical_records` vs. `training`'s `medical_certificate` records.** *Decision: unify them.* `health`'s `medical_records` (a real occupational-health record) is now the single source of truth — `safety`'s `PassportComplianceChecker` (previously reading a shape nothing ever wrote, meaning this compliance check had *always* silently failed) now reads it directly. See the new architecture follow-up below — this surfaced a real permissions gap worth a decision of its own. *Raised 2026-07-28, resolved 2026-08-12.*
- [x] **`supply_chain`'s `Asset` vs. `equipment`'s `EquipmentModel`.** *Decision: merge them.* Turned out not to be a merge — `supply_chain`'s entire `Asset` subsystem (model, 6 service methods, its `firestore.rules` block) was confirmed fully dead, zero callers anywhere. Deleted rather than merged, since there was nothing real on that side to combine. `equipment`'s model remains the sole live implementation. *Raised 2026-07-28, resolved 2026-08-12.*
- [x] **`isPremiumProvider`'s `'premium'` tier check.** *Decision: check other documents for prior decisions.* Did — found one: the billing subsystem rebuild earlier in this same session (2026-08-10) already settled this. `SubscriptionTier` is `{free, premium, enterprise}`, and the Cloud Function webhook already defaults to `'premium'` consistently. The check was already correct; the original audit was describing an old, already-replaced webhook. No code change needed. *Raised 2026-07-28, confirmed already-resolved 2026-08-12.*
- [x] **`compliance`/`contractors` naming collision.** *Decision: rename, with clarity.* Renamed the `contractors`-side identifiers (`AiComplianceService` → `ContractorPrescreenService`, the `compliance_prescreens` collection → `contractor_prescreens`, etc.) — `compliance`'s own naming was untouched since it's the module that should keep the word. *Raised 2026-07-28, resolved 2026-08-12.*
- [x] **`emergency`'s multi-site concept.** *Decision: yes, fit it into the app's existing model.* Added a nullable `propertyId`/`propertyName` to all 3 `emergency` models, referencing `property`'s existing `Property` record rather than inventing a new "Site" entity — matches the app's established pattern (an `EntitySelector<Property>` on each create form, a shared filter dropdown on each list tab). *Raised 2026-07-28, resolved 2026-08-12.*
- [x] **CRM's `Deal`/`DealStage` vs. `Opportunity`.** *Decision: merge the 2, keeping unique features from both, fitting the app's model.* `Opportunity` kept as canonical (richer, BPF-integrated, real Account/Contact FKs — `Deal`'s `customerName` was just a free-text string). `Deal`'s one real advantage, `PipelineKanbanScreen`'s drag-and-drop board, now runs on `Opportunity` instead, using its real 10-stage vocabulary. ## Architecture follow-ups

- [ ] **`PassportComplianceChecker`'s medical-records read needs a proper permissions design.** Found 2026-08-12 while fixing the item above: `medical_records`' `firestore.rules` correctly gate reads to `isManager()||isSheqOfficer()` (it's real medical data), but `PassportComplianceChecker` is reachable from `QrScannerScreen` with no role gate of its own — plausibly meant for gate/security staff who aren't managers. Currently handled defensively (a permission-denied read degrades to a "cannot verify" warning instead of crashing), but the real fix is likely a Cloud Function proxy that reads with elevated privilege and returns only the pass/fail verdict, never the raw medical record, to a lower-privileged caller. Worth deciding whether `QrScannerScreen` is actually meant to be usable by non-manager roles at all before building that. *Raised: 2026-08-12.*
