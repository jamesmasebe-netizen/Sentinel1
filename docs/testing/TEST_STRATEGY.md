# Sentinel1 Test Strategy

## Status
Phase 1 (this document + Tier 1 implementation) landed 2026-08-05. Testing infrastructure was previously **greenfield** — `test/widget_test.dart` was a 9-line boilerplate stub with no real assertions, no test packages beyond stock `flutter_test`, no Cloud Functions tests, and no CI. See [`TEST_BACKLOG.md`](./TEST_BACKLOG.md) for what's implemented vs. pending.

## 1. Scope & pyramid position (binding)

Two failure modes matter most for this app and drive everything below:
- **Silent data corruption** across the 27 tenant-scoped feature modules (a write that looks successful but produces data another screen can't read — this already happened once: `postJournalEntry` wrote Firestore field names the Dart `JournalEntry.fromJson` model didn't recognize).
- **Authorization drift** — `firestore.rules` has 116 `match` blocks; a rule that's too permissive silently leaks cross-tenant data, one that's too strict silently breaks a legitimate write. Both are invisible until someone hits them in production.

This sets a **binding rule** for where a test belongs:

| Test type | When to use | Tooling |
|---|---|---|
| Unit test (Dart) | Pure business/service logic — no Firestore reads needed to be *correct*, only to exist | `mocktail` + plain Dart |
| Provider/service test (Dart) | Riverpod providers, Firestore-backed services where correctness doesn't depend on rule enforcement | `fake_cloud_firestore` (does **not** enforce security rules — don't use it to test authorization) |
| Rules test (TS) | Anything where correctness *depends on* `firestore.rules` enforcement — tenant isolation, role gating | Firebase Emulator Suite + `@firebase/rules-unit-testing`, via `npm run test:rules` in `firebase/functions/` |
| Cloud Function test (TS) | `firebase/functions/src/*.ts` | `jest` + `ts-jest`; `firebase-functions-test` for `onCall` wrapping; emulator-backed (not deep admin-SDK mocking) for anything transactional |
| Widget test (Dart) | Screen/form rendering and interaction, deferred to Tier 3 | `flutter_test` + `ProviderScope` overrides |
| Integration test (Dart) | End-to-end golden paths, deferred to Tier 3 | `integration_test` (declared in `pubspec.yaml`, not yet used) |

**Do not use `fake_cloud_firestore` to assert anything about who is/isn't allowed to read or write something** — it has no concept of security rules and will report success on writes real rules would reject. That class of test always goes through the emulator.

## 2. Directory & naming convention

`test/` mirrors `lib/` path-for-path:
```
lib/features/finance/services/ledger_posting_service.dart
  -> test/features/finance/services/ledger_posting_service_test.dart
lib/core/bpf/bpf_orchestrator.dart
  -> test/core/bpf/bpf_orchestrator_test.dart
```
Cloud Functions unit tests are colocated: `firebase/functions/src/index.ts` -> `firebase/functions/src/index.test.ts` (same directory, `tsconfig.json` excludes `*.test.ts` from the deployed build). Rules tests live in `firebase/functions/test/rules/*.test.ts` (separate from `src/` on purpose — they require the emulator running, so they're excluded from the plain `npm test` run and only execute via `npm run test:rules`).

## 3. Riverpod override convention

Always construct a `ProviderContainer(overrides: [...])` — never instantiate a service/notifier class directly and never reach into a real `FirebaseFirestore.instance`. For `StreamProvider`-backed code (the majority of this app's data layer, per AGENTS.md's real-time-first rule), override the *provider the stream comes from* (typically `firestoreProvider`, overridden to a `fake_cloud_firestore` instance) rather than trying to fake the `StreamProvider` itself — this keeps the real provider logic (the `.tenantCollection(tenantId, ...)` calls, the `.map()` transforms) under test instead of bypassed.

```dart
final container = ProviderContainer(overrides: [
  firestoreProvider.overrideWithValue(FakeFirebaseFirestore()),
  currentTenantIdProvider.overrideWithValue('test-tenant'),
]);
addTearDown(container.dispose);
```

`tenantCollection(tenantId, path)` (`lib/core/utils/tenant_firestore_extension.dart`) resolves to `tenants/{tenantId}/{path}` — seed fixtures at that path, not at the collection root.

**Binding rule, hit twice (`safety_service_test.dart`, then again in `notifications_provider_test.dart` before this was written down): pre-warm any `StreamProvider` dependency the provider-under-test itself `ref.watch()`es, before reading the provider-under-test's own `.future`.** `userProfileProvider` is the common offender — it's an async `StreamProvider`, and providers like `notificationsStreamProvider`/`safetyServiceProvider` call `ref.watch(userProfileProvider).valueOrNull` synchronously inside their own builder. On the very first build, that value is `AsyncLoading` (not yet delivered), so the provider-under-test's *first* build often takes some "no profile yet" branch (e.g. returns `Stream.empty()`). If you then read `providerUnderTest.future`, it binds to *that* first build — and if the provider later rebuilds once the profile arrives, the already-issued `.future` does not follow the rebuild; it stays attached to the abandoned `Stream.empty()`, which never emits, and the test hangs forever (not fails — hangs, burning the full test timeout). Fix: `await container.read(userProfileProvider.future)` (or whatever async dependency is watched) *before* touching the provider-under-test, so its first real build already sees the resolved value. This applies to any provider that `ref.watch()`s another `StreamProvider`/`FutureProvider`, not just `userProfileProvider` specifically.

## 4. BPF engine testing

`lib/core/bpf/bpf_orchestrator.dart` is a pure state-transition engine (stage advancement, gating) that 14+ feature files depend on indirectly. Tier 1 covers its transition logic with in-memory fixtures — no Firestore involved, since the transition rules themselves don't touch persistence directly (the orchestrator's *callers* do the writes). The 6 domain-specific flow files (`lead_to_cash_bpf.dart`, `procure_to_pay_bpf.dart`, etc.) are Tier 2 — those need `fake_cloud_firestore` since they drive real collection writes per domain.

## 5. Cloud Functions conventions

- Wrap `onCall` functions with `firebase-functions-test`'s `wrap()` rather than calling the exported handler directly, so the real `CallableRequest` shape is exercised.
- **Every test touching a Firestore write must assert field names explicitly against the Dart model's `fromJson` keys it corresponds to** — this is the direct, non-negotiable lesson from the `postJournalEntry` bug (it wrote `date`/`totalDebit`/camelCase line fields; `JournalEntry.fromJson`/`JournalLine.fromJson` read `transaction_date`/`total_debit`/snake_case — nothing caught this until a human read both sides side-by-side). Don't just assert "a document was written" — assert its exact keys.
- Prefer emulator-backed tests (`firebase-functions-test`'s emulator mode, or direct Admin SDK against `FIRESTORE_EMULATOR_HOST`) over deep `jest.mock('firebase-admin')` mocking for anything that runs a Firestore transaction (`db.runTransaction`) — a mock can't catch a transaction that reads stale data or double-increments a balance; the emulator can.

## 6. Fixture/builder conventions

Shared fixtures live in `test/helpers/` (Dart) and `firebase/functions/test/helpers/` (TS) — e.g. `buildTestIncident({...})`, `seedJournalEntry(db, {...})`. Prefer a builder function with sensible defaults + named-parameter overrides over duplicating a full object literal in every test.

## 7. Tenant-isolation test pattern

Every rules test that touches a tenant-scoped collection asserts **both** directions: an authenticated user with the right `tenantId`/role claim can do X (allow), and a user without it cannot (deny). A rules test that only checks the allow case is incomplete — the deny case is where the actual risk lives.

**Second binding rule, also found the hard way (2026-08-07): `firebase/functions/jest.rules.config.js` must keep `maxWorkers: 1`.** Every rules test file shares ONE Firestore emulator project (`PROJECT_ID` in `rules_test_env.ts`). With Jest's default parallelism, multiple test files run concurrently in separate workers — one file's `afterEach: testEnv.clearFirestore()` can wipe out a document a *different* file just seeded, mid-test, in an interleaved run. Symptom: intermittent `FirebaseError: 5 NOT_FOUND: no entity to update`, with a failure count that varies between runs (2, then 4, etc.) — genuine flakiness, unlike the deterministic bug below. Don't remove `maxWorkers: 1` to "speed things up" without re-verifying stability across several repeat runs first; the whole suite already completes in ~10s serialized, so there's little to gain.

**Third binding rule, found the hard way (2026-08-07): call `RulesTestContext.firestore()` at most once per context, ever.** Calling it a second time on the same `authedContext(...)`/`testEnv.unauthenticatedContext()` result — even for a second, harmless read/write with no different settings — throws `FirebaseError: Firestore has already been started and its settings can no longer be changed` from `@firebase/rules-unit-testing@3.0.4`'s underlying client SDK. This is fully deterministic (not flaky — same failing tests every run), and easy to trigger by accident: any test doing more than one operation as the same user (`setDoc` then `getDoc`, or building a doc ref then later calling `.firestore()` again to delete it) hits it. Fix: call `.firestore()` exactly once, store the result (or a `doc()`/`collection()` ref built from it) in a local variable, and reuse that for every subsequent operation in the test — never call `.firestore()` a second time on the same context object. This was root-caused after several wrong theories (worker parallelism, total context count, `unauthenticatedContext()` specifically) all failed to explain it; the real trigger is exactly and only "more than one `.firestore()` call on one context."

## 8. Widget testing convention

Established with the first real widget-test pass (T3-WIDGETS: `incident_report_form_test.dart`, `journal_entry_form_test.dart`, `document_review_dialog_test.dart`, `safety_file_submission_view_test.dart`). Same spirit as §3's `ProviderContainer` convention, adapted for a real `testWidgets`/`pumpWidget` pump. Shared scaffolding lives in `test/helpers/widget_test_harness.dart` (`buildLoggedInContainer`, `buildMockOfflineSync`, `hostedUnderPushedRoute`/`hostedDirectly`/`hostedDialogTrigger`).

- **`Firebase.initializeApp()` is never called in a test, full stop — this is a hard limit, not a workaround.** Every screen under test must reach Firebase exclusively through Riverpod-overridable providers. Set `isMockLoggedInProvider.overrideWith((ref) => true)` — this makes `userProfileProvider`/`currentTenantIdProvider` short-circuit to a canned identity (`uid: 'dev-admin-123'`, `tenantId: 'sentinel-dev'`) *before* either ever reaches `authStateProvider`/`FirebaseAuth.instance`, which is what makes avoiding `Firebase.initializeApp()` possible for a full widget pump at all. For a test that specifically needs the *real* (non-mocked) auth chain, override `firebaseAuthProvider` with `firebase_auth_mocks`' `MockFirebaseAuth` instead — a pure-Dart fake with no platform channel.
- **Prefer `UncontrolledProviderScope(container: ...)` over a bare `ProviderScope(overrides: [...])`.** Keeps a handle on the container after pumping — for post-pump provider reads (e.g. subscribing to `appEventBusProvider.stream` before submitting) or for pre-warming a `StreamProvider` before the first pump (see next point). `buildLoggedInContainer()` returns exactly this.
- **The `userProfileProvider` pre-warm race (§3) applies to widget pumps too, and extends to any `StreamProvider` fixture data a screen depends on.** `userProfileProvider`'s mocked branch is still an `async*` generator — its first `yield` lands on a microtask, not synchronously with `pumpWidget()`. Always `await container.read(userProfileProvider.future)` (and any other `StreamProvider` a screen watches, e.g. `glAccountsStreamProvider`) *before* `pumpWidget()`, then follow `pumpWidget()` with at least one bare `await tester.pump()` before any assertion depends on resolved data. Widgets in this codebase fail safely while loading (`EntitySelector`/`EmployeeSelector` render a disabled dropdown, not a hang) — this is a correctness issue for assertions, not a hang risk, but it silently makes "select an item" interactions fail if skipped.
- **Never `pumpAndSettle()` across a toast/SnackBar-triggering action, in either direction.** Both `UIUtils.showToast` (4s duration) and a raw `ScaffoldMessenger.showSnackBar` (some screens bypass `UIUtils.showToast` — a real, pre-existing convention deviation, flag it in the test file when found, don't silently "fix" it into a behavior change) will hang `pumpAndSettle()` waiting for the SnackBar's own dismiss timer. Use targeted `pump()`/`pump(duration)` steps instead. If a toast and a `Navigator.pop(context)` fire back-to-back with no `await` between them (a common pattern in this codebase), don't fight to assert the toast text is *stably* visible — its host `Scaffold` may already be mid-teardown by the next frame. Assert the underlying state change instead (the write that happened, the route that popped).
- **The offline-queue write is fire-and-forget under `WidgetTester` too (see `test/core/services/offline_sync_service_test.dart`'s finding).** `FirestoreService.createDocument`/`updateDocument` resolve once `OfflineSyncService.queueOperation` finishes writing to the Hive queue box, not once the write actually lands in Firestore. Since a real `OfflineSyncService`'s Hive box is never initialized outside `main.dart`'s boot sequence anyway (a real write attempt throws `LateInitializationError`), override `offlineSyncServiceProvider` with `buildMockOfflineSync()` (a mocktail mock with `queueOperation` stubbed to resolve) for any screen that writes through `FirestoreService` — then assert the **captured `queueOperation` call args** (collection path + data map), not a document landing in the fake Firestore, since with the mock in place nothing actually reaches it. A couple of `pump(const Duration(milliseconds: 50))` steps after tapping submit are usually enough; a chain of 2+ sequential `FirestoreService` calls (e.g. an incident write followed by an auto-CAPA write) may need one more.
- **Wrap the widget under test in a real host route, not bare `MaterialApp(home: ...)`, if its submit flow calls `Navigator.pop(context)`.** Use `hostedUnderPushedRoute()` (pushes via `Navigator.push(MaterialPageRoute(...))` from a trigger button) or `hostedDialogTrigger()` (opens via the widget's own `showDialog`-based static `.show()` entry point, which also solves the "needs a route to pop into" problem for free). After the pop/dialog-close fires, advance past the route's exit transition explicitly — `await tester.pump(const Duration(milliseconds: 400))` for a `MaterialPageRoute` (~300ms default transition), `~300ms` for a dialog route — a single bare `pump()` only advances one frame and the popped widget will still be found mid-animation.
- **A plain `ListView(children: [...])` (not `.builder`) still only mounts elements within the viewport + cache extent — this is a Sliver-rendering property, not a builder-vs-list-literal difference.** A long form (20+ fields before the interesting part) will silently fail every `find.text()`/`find.widgetWithText()` call for anything below the fold, with no error — it looks exactly like a wrong selector. Either scroll explicitly (`tester.scrollUntilVisible`/`dragUntilVisible`) between every off-screen interaction, or set a tall test surface once per test (`await tester.binding.setSurfaceSize(const Size(w, h)); addTearDown(() => tester.binding.setSurfaceSize(null));`) so the whole form is "visible" at once — the latter is far less tedious for forms with many fields.
- **A widget-level `Provider` that hardcodes a Firebase singleton as a class-*field* initializer (not inside a method body) cannot be avoided by simply not tapping the button that uses it** — a field initializer runs the instant `createState()` builds the State object, before any Riverpod override or button-tap logic runs. If found, and the value is genuinely only needed inside one deferred method, converting the field to a lazy **getter** (evaluated only when that method actually runs) is a small, behavior-preserving, in-scope fix — not the same as inventing a new architecture. A `Provider` itself hardcoding a Firebase singleton (rather than a widget's own field) is different: override the *provider* directly with a real instance built from test doubles, since the provider is already the intended seam.
- **A label used as both a header field's `labelText` and a repeated per-row field's `labelText` (e.g. "Description" on both a form's header and each of its line items) makes `find.widgetWithText(...)` ambiguous** — Flutter's finder throws "Too many elements" from deep inside `enterText`/`tap`, not a helpful "found 3, expected 1" message. Disambiguate with `.first`/`.at(index)`, documented inline with what each index means.

## 9. Integration tests and CI coverage thresholds

**CI coverage thresholds (T3-CI-COVERAGE):** `.github/workflows/test.yml`'s `flutter-checks` job runs `flutter test --coverage` and gates on `VeryGoodOpenSource/very_good_coverage@v3` against `coverage/lcov.info`; `functions-checks` runs `npm test -- --coverage`, which enforces `firebase/functions/jest.config.js`'s `coverageThreshold`. Both floors are set a few points below the measured baseline at the time they were added (~58.6% Flutter lines, ~41% functions lines/statements) as **regression gates, not aspirational targets** — ratchet them up as real coverage grows; never lower a threshold just to get a failing PR green. The functions-side number only covers the fast, non-emulator `npm test` run (TEST_STRATEGY.md §2's deliberate split from the emulator-backed `test:rules` suite) — it does not reflect the fuller coverage the emulator-backed write-path tests provide, and merging the two isn't done here.

**`integration_test`:** unlike every other test in this suite, `integration_test/*.dart` files run the REAL app assembly — real `Firebase.initializeApp()`, real `GoRouter`, real `AuthService` — against the **local Firebase Emulator Suite** (not production), per §1's binding mock-vs-emulator rule: this is exactly the class of test ("correctness depends on `firestore.rules` enforcement") the emulator exists for. They do not call `lib/main.dart`'s `main()` directly; each test replicates the relevant parts of its bootstrap (Firebase init, Hive, the `ProviderContainer`) redirected at `localhost` emulator ports, so production boot code is never touched for test purposes. A `belongsToTenant()`-gated write (e.g. reporting an incident right after `AuthService.devBypassLogin()`) needs the **Functions emulator running too**, not just Auth+Firestore — `firestore.rules` reads `request.auth.token.tenantId`, an Auth custom claim, and nothing sets it except the `syncUserClaims` Firestore-trigger Cloud Function reacting to the `users/{uid}` profile write; poll/retry for the claim to appear on a refreshed ID token rather than assuming a fixed delay is enough (this is a real, pre-existing race in `devBypassLogin()` itself, not a test artifact). Run via `firebase emulators:start --only auth,firestore,functions` (after `cd firebase/functions && npm run build`), then `flutter test integration_test/<file>.dart -d <device>`.

**Local environment note (this machine specifically, may not apply elsewhere):** this project's checked-in Android Gradle Plugin (8.7.0, `android/settings.gradle.kts`) was too old for the AndroidX Camera dependencies `image_picker_android` pulls in (needs AGP 8.9.1+) — bumped to `8.9.1` with the Gradle wrapper bumped to `8.11.1` to match (T3-INTEGRATION). A full macOS/iOS build needs Xcode (not just Command Line Tools) and wasn't available in the environment this was first run in; Chrome/web isn't supported by `flutter test integration_test/` at all. An Android emulator was the only viable local target — `adb reverse tcp:<port> tcp:<port>` for 9099/8080/5001 is what lets the emulator's `localhost` calls reach the host machine's emulator suite.
