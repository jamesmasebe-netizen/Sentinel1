**CRITICAL FINDING #1 — security vulnerability, confirmed live 2026-08-07:** while writing this cluster's role-gated-read tests, 3 failed with "expected request to fail, but it succeeded": `medical_records`, `coida_claims`, `coida_compliance_checklist` were all readable by a plain `employee`, despite each declaring its own `isManager() || isSheqOfficer()` read gate. Root cause, confirmed via an isolated throwaway test against `payroll_ledgers` (a collection none of this session's test files had touched): **Firestore evaluates every structurally-matching `match` block for a path and grants the request if ANY of them allows it — not "most specific wins."** The tenant-scope catch-all block —
```
match /{collection}/{docId} {
  allow read: if belongsToTenant(tenantId);
  allow write: if false;
}
```
— structurally matches every already-declared collection's paths too, and its unconditional `read: if belongsToTenant(tenantId)` silently overrode every collection's own tighter read rule. Blast radius (every collection in the schema with a role-gated read, confirmed by grepping every `allow read:.*&&` in the file): `medical_records`, `coida_claims`, `coida_compliance_checklist`, `job_applications`, `payroll_ledgers`, `compensation_plans`, `performance_reviews`, `disciplinary_records`, `benefit_enrollments`, `invites`, `candidates` — 11 collections' read restrictions were silently unenforced for any authenticated same-tenant user, regardless of role. **Fix:** tightened the catch-all to `allow read, write: if false;`.

**CRITICAL FINDING #2 — availability bug, likely more severe in practice, found while assessing the fix's blast radius:** tightening the catch-all's read to `if false` is only safe if nothing legitimately depends on it. Cross-referencing every `tenantCollection(tenantId, 'name')` call in `lib/` against every declared block in `firestore.rules` turned up 9 real, actively-used-in-app-features collections with **no declared rule at all**, relying entirely on the catch-all: `audit_logs`, `counters`, `actuals`, `expenses`, `timeEntries`/`time_entries` (naming-drift duplicate — `project_providers.dart` and `pmo_service.dart` write two different collection names for what looks like the same concept), `departments`, `job_roles`, `ohs_roles`, `competency_passports`, `skills_matrix`. Since the catch-all's `write` was already `if false`, **every write to these was already being rejected by real, rules-enforced Firestore** — including, critically, `audit_logs`: `FirestoreService.createDocument`/`updateDocument`/`deleteDocument`/`directCreate`/`directUpdate`/`batchWrite` (`lib/core/services/firestore_service.dart`) all `await AuditLogService.logAction(...)` **unconditionally, unguarded by try/catch, before doing the real write**. Confirmed empirically with a throwaway emulator test: an `audit_logs` write is denied for every role, including admin (`PERMISSION_DENIED: false for 'create' @ L706, false for 'create' @ L718`). This means **any write routed through `FirestoreService` — at least 13 files' worth, including this session's own Wave 2b Compliance/Health/WorkersComp/Emergency/Risk extractions — currently throws and fails before the real data write happens, against any real, rules-enforced Firestore.** (Plausible this has gone unnoticed because the project isn't yet exercising a real Google sign-in / rules-enforced environment in practice — see `sentinel1_admin_access.md`/`sentinel1_deploy_blockers.md` memory notes on the anonymous dev-bypass admin account and the Spark-plan deploy block.) **Fix:** added explicit `match` blocks for all 9 collections (plus `audit_logs`), each modeled on the closest analogous already-declared collection and the collection's real read/write usage in `lib/` (e.g. `counters` mirrors `fcm_tokens`'s open tenant read+write since it's a transaction-internal ID-generation counter; `departments`/`job_roles`/`ohs_roles` mirror `employees`'s open-read/manager-write/admin-delete shape; `audit_logs` gets manager-only read since it's a security/oversight trail, open create since any role can trigger a write as a side effect, and no update/delete since entries are immutable).

**Not fixed (out of scope for this pass, flagged for follow-up):** 5 more names (`chart_of_accounts`, `cost_centers`, `invoices`, `knowledge_articles`, `tickets`) and 8 more (`action_trackers`, `budget_plans`, `dispatchers`, `field_agents`, `journal_entries`, `project_tasks`) appear in `lib/scripts/seed_production_data.dart`/`seed_dummy_data.dart` only — one-off data-seeding scripts, not real user-facing runtime paths, most using pre-rename collection names where the real app now uses a prefixed name (e.g. the script writes `chart_of_accounts`, the app and rules use `fin_chart_of_accounts`). ### T2-BPFORCHESTRATOR: BPF orchestrator investigation — 1 real bug fixed, 1 larger architectural gap found and deliberately left unfixed

**File(s):** `lib/features/projects/models/project_models.dart` (fixed) -> `test/features/projects/models/project_models_test.dart` (new, 3 tests). `lib/core/bpf/bpf_orchestrator.dart` — **investigated, a fix was attempted and then reverted; not fixed.**
**Why:** `BpfOrchestrator` (`lib/core/bpf/bpf_orchestrator.dart`) is the last remaining Tier 2 BPF gap per the Module -> Tier cross-reference ("domain flows") and `TEST_STRATEGY.md` §4 — 9 methods across all 6 domain flows, tying together writes across 7 different services, never tested. Investigating it to scope its first tests (not writing product code) surfaced two real bugs before any test was written.

**Bug 1 — FIXED, regression-tested: `Project.toFirestore()`/`fromFirestore()` field-name mismatch, unrelated to BPF but found while reading the same file.** `toFirestore()` wrote the tenant-scoping field as `'tenantId'`; `fromFirestore()` read it back as `data['siteId']` — and every query that filters this collection (`projectsProvider` in `project_providers.dart`, plus `gantt_task_editor_sheet.dart`, `assign_contractor_dialog.dart`, `safety_compliance_data_fetcher.dart`) filters on `'siteId'`, the convention every other tenant-scoped collection in this app already follows. Confirmed via `projectsProvider`'s consumers (`grep`) that this is a live, widely-used provider — feeding `project_operations_hub_screen.dart`, `project_dashboard_screen.dart`, `schedule_board_screen.dart`, `control_tower_screen.dart` (the main dashboard), `journal_entry_form.dart`, and `contractor_inductions_tab.dart`. **Net effect: every project ever created through the normal "New Project" dialog has been invisible to all 6 of those screens**, and `project.tenantId` always read back as `''`, so `safety_compliance_data_fetcher.dart`'s risk/permit/action-item lookups and `assign_contractor_dialog.dart`'s contractor lookup were silently querying tenant `''` instead of the real tenant. Fixed by writing `'siteId'` instead of `'tenantId'` (one line) — matches the codebase-wide convention, and required no changes to any of the (already-correct) `'siteId'`-filtering queries. 3 new tests in `test/features/projects/models/project_models_test.dart`: a written project is findable via the exact `siteId`-filtered query `projectsProvider` uses, `tenantId` round-trips correctly, and a doc written with the old buggy shape is confirmed NOT found (proving the bug this test guards against was real, not hypothetical). `flutter analyze` clean on both files. **No data migration was performed** — any project documents already written with the old, broken field name remain invisible until re-saved; given this project's current dev/pre-launch state (see `sentinel1_admin_access`/`sentinel1_deploy_blockers` — anonymous dev-bypass auth, no Blaze plan yet), existing seeded data is assumed disposable rather than requiring a backfill script, but this should be verified before any real launch.

**Bug 2 — found, NOT fixed, needs a product decision:** `BpfOrchestrator.createProjectFromQuote` (the Lead-to-Cash step that turns an accepted Quote into a Project) writes through `PmoService`/`pmo_models.dart`'s `Project` class — a completely different schema than `project_models.dart`'s `Project` (no `stages`, no `budget` as a number, `projectManagerId` instead of `projectLead`, `endDate` instead of `targetEndDate`, a nested `timestamps.createdAt` instead of a flat `createdAt`, millisecond-timestamp IDs instead of the sequential `PRJ-001` scheme). Both write to the same `tenants/{tenantId}/projects` collection. **Attempted fix:** reroute `createProjectFromQuote` to build a `project_models.dart` `Project` (with real stages, mirroring `new_project_dialog_content.dart`'s exact shape) and call `ProjectService.createProject` instead — this is what a project created through the normal "New Project" dialog does, and would make Lead-to-Cash-generated projects visible to `projectsProvider`'s 6 consumers (Bug 1's fix made that path finally reachable). **Reverted before committing**, because further investigation found `createInvoiceFromProject` (the very next step in the same Lead-to-Cash flow) needs `project.clientId`/`project.revenueRecognitionMethod` — fields that exist only on `pmo_models.dart`'s `Project` — and its one real caller, `project_detail_screen.dart` (singular "detail"), is reached directly from `quote_detail_screen.dart` immediately after `createProjectFromQuote` returns (confirmed by reading the navigation call site). **This means there are two separate, both-real, both-currently-reachable "Project" screens/subsystems built on incompatible schemas sharing one collection:** `project_models.dart` + `project_providers.dart` + `project_details_screen.dart` (plural) + `project_operations_hub_screen.dart` + `new_project_dialog_content.dart`, wired into the main app router — versus `pmo_models.dart` + `pmo_providers.dart` + `project_detail_screen.dart` (singular) + WBS tasks + invoice generation, wired into the CRM quote-acceptance flow. A project created via `createProjectFromQuote` currently satisfies only the second; making it satisfy the first (my attempted fix) would have broken the second, which is the one immediately, verifiably exercised right after quote acceptance. Reconciling this — pick one schema and migrate the other's screens onto it, or have the write path populate both — is a genuine architectural decision, not a bug fix, and wasn't attempted.

**BPF orchestrator tests themselves: not yet written**, deferred pending the Bug 2 decision above — testing `createProjectFromQuote` meaningfully requires first knowing which `Project` shape it's supposed to produce. The other 8 `BpfOrchestrator` methods (Lead-to-Opportunity, Opportunity-to-Quote, Quote-acceptance's Invoice step, all 3 Procure-to-Pay steps, Asset deployment, CAPA-from-Incident, Onboarding-completion) don't depend on this and could be tested independently — flagged as the concrete next step once picked back up.
